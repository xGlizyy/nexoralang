Language guide

NEXORA, as it works today

A short tour of what the current interpreter (version 0.2) accepts. Every program on this page is run by the project's tests, and every one can be tried in the playground.

NEXORA is in early development. The syntax may change, and the language is still small: the limitations are listed at the end.

Introduction

A program is one .nex file. It starts running at the function main. print writes a value followed by a line break.

Before running anything, NEXORA checks the whole program: names, types and whether every function returns what it promises. A program with an error is never started.

Syntax

  • A statement ends at the end of its line. There are no semicolons.
  • Blocks are written with braces. Indentation is free.
  • A comment starts with // and runs to the end of the line.
  • let declares a variable. Variables never change: there is no reassignment.
  • A name can only be declared once while it is visible. There is no shadowing.
  • Text is written between double quotes, on one line.

Types

The type of a variable is inferred from its value, or written after a colon. All types are known before the program runs, so a type error can never appear while it is running.

Nothing is converted implicitly. An Int and a Float are never mixed, and a number is never joined to a text. Conversions are explicit calls: to_float, to_int and to_text.

Multiplication and division come before addition and subtraction, then comparisons, then and, then or. Dividing two Int gives an Int: the fractional part is dropped. Comparisons cannot be chained.

Functions

Every parameter states its type, and the return type is always written. A function that returns a value must end with return on every path. if and else choose between blocks; the condition must be a Bool. There are no loops yet: repetition is written with recursion.

Contracts Experimental

A function can state what it expects from its caller (requires) and what it promises (ensures, where result is the value returned). The clauses go at the start of the body. They are checked while the program runs, on every call: they are not proven in advance. This part of the language may change.

Diagnostics

When something is wrong, NEXORA says what kind of problem it is, where it is, and what was expected. Each problem has a stable code. This program has a type error, found without running it:

KindMeaningFound
lexicalA character that is not part of the languageBefore running
syntaxThe code does not follow the grammarBefore running
semanticNames, scopes, return pathsBefore running
typeTypes that do not matchBefore running
runtimeDivision by zero, overflow, endless recursionWhile running
contractA requires or ensures condition was falseWhile running

In the playground, selecting a diagnostic shows its position in the editor.

Limitations

These do not exist yet. Using them is an error, not something the playground pretends to support:

  • Loops and variables that can be reassigned.
  • Lists, records and any other compound type.
  • Operations on text other than joining and comparing for equality.
  • Reading input, files or the network: a program can only print.
  • Modules: a program is a single file.
  • Any integration with AI models.

Limits of the implementation:

  • At most 1000 nested calls.
  • Int is a 64-bit integer; going out of range stops the program.
  • In the playground, a program is stopped after a time limit and if it prints too much.

The interpreter is a reference implementation: it has not been measured for speed, and NEXORA is not ready for production use.
